# 7. CLOUDFLARE / PYCFLARE REQUIREMENT

Follow the Cloudflare boundary defined by `AGENTS.md`.

The current production media provider architecture is:

```text
Cloudflare R2
    → audio
    → arbitrary binary objects
    → source media
    → captions/waveforms/general objects

Cloudflare Images
    → artwork
    → photographs
    → image variants
    → private/gated images

Cloudflare Stream
    → video podcast ingest
    → video processing/encoding
    → adaptive playback
    → private video
```

Python-side Cloudflare integration must use the project's required `pycflare` package and SANFootball's provider-adapter boundaries.

Do **not** introduce parallel:

* raw Cloudflare REST implementations;
* direct `boto3` implementations for R2 where `pycflare` supplies the required capability;
* another unrelated Cloudflare SDK;
* Cloudflare-specific calls scattered through domain services.

Keep domain ownership provider-neutral even though the concrete production implementation currently uses Cloudflare.

Protected media must use short-lived authorization/capabilities rather than permanent private URLs.

Never log provider credentials, upload capabilities, signing secrets, API tokens, R2 credentials, Stream secrets, or Images signing material.

# 8. DOMAIN DESIGN RULES

Maintain clear domain boundaries.

Prefer the governing dependency pattern established in `AGENTS.md`.

Domain logic must not depend on presentation logic.

Prefer:

```text
API / View
    ↓
Service / Policy / Selector
    ↓
Domain Models
```

Avoid:

```text
Domain Service → DRF Serializer
Domain Model → API View
Recommendation Domain → REST Serializer
```

Use:

* models for state and local invariants;
* selectors for reusable read/query composition;
* services for transactional use cases/state transitions;
* policies for authorization/business decisions;
* tasks for asynchronous orchestration;
* API modules for HTTP/presentation concerns.

Do not mechanically create layers that provide no value.

# 9. CRITICAL STATE TRANSITIONS

Critical state transitions must be explicit, transactional, testable, and observable.

Do not hide important business operations inside arbitrary signals or model `save()` methods.

Examples include:

* subscription activation;
* subscription cancellation;
* entitlement grant/revocation;
* billing webhook handling;
* queue creation/reordering/merging;
* protected download authorization;
* protected media access;
* media lifecycle transitions;
* creator ownership/permission changes;
* live broadcast lifecycle where implemented.

Signals may support secondary concerns such as:

* cache invalidation;
* metrics;
* safe non-critical reactions.

Do not make them the only execution path for financially or operationally critical behaviour.

# 10. DATABASE AND CONCURRENCY

Move durable invariants into PostgreSQL where appropriate.

Use deliberately:

* foreign keys;
* unique constraints;
* check constraints;
* conditional constraints;
* indexes;
* transactions;
* row locking such as `select_for_update()` when necessary.

Analyse concurrency for every mutable ordered/shared state.

Do not rely solely on application-level checks when invalid state can be prevented by the database.

High-traffic read paths must avoid N+1 query patterns and unbounded collections.

Use appropriate:

* `select_related`;
* `prefetch_related`;
* `Prefetch`;
* annotations;
* aggregates;
* pagination;
* query-count tests.

Do not add speculative indexes without evidence from actual query patterns.

---

# 11. ASYNC AND CELERY RULES

Heavy work belongs outside normal request paths.

Use background workers appropriately for:

* media processing;
* transcription;
* summaries;
* recommendations;
* search indexing where required;
* notifications;
* analytics aggregation;
* webhook follow-up;
* cleanup;
* AI/ML processing.

Tasks must be:

* bounded;
* retry-safe where retrying is possible;
* idempotent where duplicate delivery is normal;
* observable;
* structured in logging;
* explicit about failure;
* conscious of memory use;
* conscious of transaction boundaries.

Separate worker queues where workload characteristics justify it.

Media/transcription/ML workloads must not starve ordinary operational or billing tasks.

Do not perform ML model training at Django import/startup time.
